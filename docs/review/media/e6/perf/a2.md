# E6 A2: load tail or night cost, the first-use frames, the gate rule, the boot cost

Device: iOS Simulator "iPhone 17 Pro", iOS 26.5, Safari, profile web build (macOS 26.4.1), fixture `tier3_cap_threat` (day 24, tier-3 cap night, threat branches). Builds: profile exports of the branch at `3b2eb7e` plus the working tree of this task (the build changed between batches only by log markers, then by the guard-bar and diner-fade warm-up additions; each table says which). Every run began at 75% idle or more; mid-run idle 52 to 72% as always (the Simulator is in it). Runs were taken in batches of at most three with the perf lock; crops under `a2/`, names in the tables (`lognight_r1_crop.png` ...), one full screenshot `a2/play_r1_full.png`.

## 1. The frame log (`?perflog=<s>`, `ui/perf_overlay.gd`)
Records every frame of the first <s> seconds after each phase change (`t` = seconds since the phase change, `ms`), prints one `PERFLOG` console line and shows on screen: `phase_msec` (engine ticks at the phase change), `stable_at` (when the boot fade lifts), the frames of 30 ms or more with the draw calls / node count / video memory change of that frame, and the first use of each event (`wave0@`, `fx_poof@`, `guard_hit@`, `banner_off@`, `bootfade_gone@`, `fade_Diner@`, ...). Inert without the flag (a unit test pins it). Flush cost: the print is about 0.5 s, so the reading of a log run is not a reading (`worst 484 ms @ 23.5 s` in the 25 s log runs is the flush itself).

## 4. The north-lane frame: its trigger is the diner's first fade; it is NOT a first-use draw (D-292 follow-up)
Facts (frame log, play-entered night, tier-3 cap, `?perflog=60`): a single frame of 113 to 148 ms at wave 1 + 11.0 to 11.8 s (night 52.6 to 54.8 s) in every run; script time normal, nodes and video memory unchanged, 83 draw calls against 72 around it. It follows the lane: absent with wave 1 on west/east or on sw/east, present with west/north; independent of the fence and tower branches (`tier3_cap_all_a`, `all_b`, `threat`).
Tagged event (new marker `fade_Diner@<t>`: the first frame the diner's occluder fade is active): `nf_def_r1` (default): `fade_Diner@54.40`, spike 148 ms @54.5 (the next frame after the tag).
Discriminating run (`?perfnofade=1`: `OccluderFade` processing disabled by the overlay): `nf_off_r1`, `nf_off_r2`: no `fade_Diner` tag, NO frame above 38 ms before the log's own flush at 60 s (the 70 / 65 ms at 58.1 s of the window is the 60 s log's print, as in every log run); with the fade on in the same build the frame is 148 ms. So the fade's first activation is what makes the frame.
Is it a first-use draw? Three warm-up attempts, each measured against the same build without it (three gate runs per row, play-entered, default window, `?perfglyph` default on):
| warm-up variant | runs: worst ms (top-3 other frames) |
|---|---|
| none (`gbefore_r1..3`, build = guard-bar warm-up only) | 126, 117, 117 (median 117); avg fps 49.6 / 50.5 / 51.1 |
| force the real diner faded during the warm-up's frames (`gafter_r1..3`) | 131, 117, 121 (median 121); the diner is off screen then, so nothing is drawn |
| faded copy of EVERY distinct diner material on boxes in the warm-up grid (`gafter2_r1, r3`; r2 never left the loading screen, discarded) | 130, 118 (median 124) |
| faded miniatures of EVERY diner mesh (same Mesh resources, same blended materials, scale 0.04) in one grid slot (`gafter3_r1..3`) | 132, 120, 117 (median 120) |
No variant moves the frame (all within the 117 to 131 ms spread of the build without it), so it is not a shader or material first draw that a warm-up can cover: all four are the same frame. NOT COMMITTED: the warm-up for it.

### 4b. Prebuild the faded materials at setup (the main session's reading of `OccluderFade`), measured
Change tried (not kept): `components/occluder_fade.gd` builds every faded duplicate in `refresh_bounds` and keeps them for the building's lifetime; a fade start only swaps overrides, `_restore` swaps back and keeps the entries (a `duplications` counter, unit tests: no duplication at fade start, the same copies reused, a new mesh prebuilt and a freed one dropped; 33 of 33 in `test_occluder_fade.gd`, the 30 existing ones unchanged). Three gate runs (`v1_r1..3`, play-entered, glyph prime on): **116, 119, 118 ms, median 118** against 117 without it (`gbefore`): the frame survives.
Why prebuilding could not matter, measured: the diner is ONE `MeshInstance3D` with two surfaces (tier 1 and the tier-3 art alike), plus one `Label3D`. The first fade's whole `_apply` (with the copies already built) takes **2.0 ms** of script time (`fade_apply_2.0ms@54.48 fade_meshes1_labels1@54.48` in the frame log, `v1log_r1..2`: 2.0 ms in both), against a 118 / 124 ms frame at the next tick (`54.6:118`, `54.7:124`; script time p15 and 83 to 85 draw calls against 72 around). So (a) the duplicate()s are two, not N, and (b) variant 2 (spreading the swap over frames, nearest mesh first) has nothing to spread: one mesh. I did not implement a per-surface spread (two surfaces).
Where the time goes (step 3): not in the fade's script (2.0 ms) and not in the node count or video memory (unchanged at the frame): it is on the render side, in the frame that first draws the diner in the transparent pass: +11 draw calls, and a forced fade of faded copies of every material / mesh in the warm-up (4a) left it unchanged. It is the visual question for the author: the first blended draw of the large merged diner mesh costs about 100 ms on this device (the Compatibility renderer's transparent pass or a per-material program the warm-up cannot reach). Candidates, not tried (they change visuals): a dithered / alpha-scissor fade (no blending pass), fading by hiding the wall nearest to the camera instead of blending the whole building, or splitting the diner mesh so the fade blends only the surfaces that hide the hero.
Reverted: `components/occluder_fade.gd`, `tests/unit/test_occluder_fade.gd` and the overlay's `fade_apply` marker are back at the committed state (no tier-1 code changed, so no determinism baseline is needed for this task); kept as evidence only: `v1_r1..3`, `v1log_r1..2` crops.

## 6. Boot warm-up cost (`?warmup=0`), three loads each (frame-log lines `phase_msec` and `stable_at`)
First playable frame = `phase_msec` (engine ticks at the phase change, after the warm-up) + 1000 x `stable_at` (when the boot fade lifts: 10 frames in a row under 50 ms).
| | run 1 | run 2 | run 3 | mean |
|---|---|---|---|---|
| warm-up on: phase_msec / stable_at | 3624 / 1.78 | 3577 / 1.75 | 3629 / 1.79 | |
| warm-up on: first playable (s) | 5.40 | 5.33 | 5.42 | 5.38 |
| `?warmup=0`: phase_msec / stable_at | 1669 / 3.02 | 1690 / 2.93 | 1689 / 3.00 | |
| `?warmup=0`: first playable (s) | 4.69 | 4.62 | 4.69 | 4.67 |
With the guard-bar boxes (the committed warm-up, `lognight2_r1..3`): phase_msec / stable_at 3593 / 1.67, 3844 / 1.75, 3690 / 1.76 = first playable 5.26, 5.59, 5.45 s, mean 5.43 s: the warm-up costs 0.76 s against `?warmup=0` (4.67 s); the two extra boxes cost about 0.05 s. The warm-up (before the guard bars) costs 0.71 s of load to first playable frame (it delays the phase change by 1.95 s but shortens the load freeze after it from 2.6 s to 1.5 s). What it buys (frame log, `w0_r1..3` against `lognight_r1..3`): without it the first seconds hold 2487 to 2601 ms (the freeze), 178 and 154 ms at 2.8 s (2 of 3), and in the resumed night 116 / 118 / 118 ms at 12.7 to 12.8 s and 99 / 97 / 96 ms at 14.2 to 14.3 s (the first kill, `fx_poof` and `fx_hit` at 14.1 to 14.2 s); with it, the freeze is 1.5 s and the 12 s and 14 s frames are gone (13.2 s: no frame of 30 ms or more).
