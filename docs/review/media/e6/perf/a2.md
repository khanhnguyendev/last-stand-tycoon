# E6 A2: load tail or night cost, the first-use frames, the gate rule, the boot cost

Device: iOS Simulator "iPhone 17 Pro", iOS 26.5, Safari, profile web build (macOS 26.4.1), fixture `tier3_cap_threat` (day 24, tier-3 cap night, threat branches). Builds: profile exports of the branch at `3b2eb7e` plus the working tree of this task (the build changed between batches only by log markers, then by the guard-bar and diner-fade warm-up additions; each table says which). Every run began at 75% idle or more; mid-run idle 52 to 72% as always (the Simulator is in it). Runs were taken in batches of at most three with the perf lock; crops under `a2/`, names in the tables (`lognight_r1_crop.png` ...), one full screenshot `a2/play_r1_full.png`.

## 1. The frame log (`?perflog=<s>`, `ui/perf_overlay.gd`)
Records every frame of the first <s> seconds after each phase change (`t` = seconds since the phase change, `ms`), prints one `PERFLOG` console line and shows on screen: `phase_msec` (engine ticks at the phase change), `stable_at` (when the boot fade lifts), the frames of 30 ms or more with the draw calls / node count / video memory change of that frame, and the first use of each event (`wave0@`, `fx_poof@`, `guard_hit@`, `banner_off@`, `bootfade_gone@`, `fade_Diner@`, ...). Inert without the flag (a unit test pins it). Flush cost: the print is about 0.5 s, so the reading of a log run is not a reading (`worst 484 ms @ 23.5 s` in the 25 s log runs is the flush itself).

### 2.3 The window-start frame is a measurement cost: confirmed
Evidence A (A1, repeated here): the frame moves with the window (`perfwarm` 2 / 3 / 5: 2.1 / 3.1 / 5.1 s). Evidence B (new): `?perfglyph=1` (an experiment flag of the overlay: draws every glyph both labels will ever show once, in the first frame, under the boot fade) with the default window removes it:
| build | resume, default window, worst 3 | worst |
|---|---|---|
| A1 default (3 runs) | 128 @0.2 / 95 @0.1 / 133 @0.2 | median 128 |
| `glyph_r1..3` (`perfglyph=1`) | 35 @55.2 (w1 +12.9) / 27 @44.9 / 38 @0.2 | 35, 27, 38: median 35 |
So the 95 to 149 ms frame is the first rasterisation of the overlay's own digits when its label first shows numbers (the 2nd frame after the window opens, which is why it reads `@0.1`); it is not a frame of the game. The same flag shows nothing else at 2.1 to 2.2 s.

## 4. The frame that decides the gate in a night entered by play: wave 1 + 11.7 s (north lane)
Three of three play-entered runs, plus the log runs `playlog60_r1..2`, `playx_r1..2`, `playa`, `playb`, `playswe`..., read one frame of 113 to 129 ms (script time 15 to 17 ms, node count and video memory unchanged, 83 draw calls against 72 around it) at 52.7 to 54.8 s: wave 1 + 11.0 to 11.7 s. It is a REAL frame at a fixed moment of the night (not the window: the same moment in every run), independent of the tower and fence branches, and it belongs to the NORTH lane: the first time the north lane's enemies (they come down behind the diner, off the hero's side of it) appear. The resumed night shows the same moment at 33 to 35 ms (`glyph_r1`: 35 @55.2, w1 + 12.9), because the hero there stands north of the diner. What I could not establish is the visual: candidate (hypothesis, not shown): the diner's first fade. `World._occluder_targets` includes every alive Boar and the hero; `OccluderFade` swaps all the diner's meshes for transparent duplicates the first time one is hidden behind it, which for a hero standing in front of the building is the first north-lane boar. It matches the lane, the 11 extra draw calls, the absence of any node or memory change, and the smaller resumed-night frame; the sw lane's enemies never pass behind it. A warm-up that draws the real diner faded (a `Warmup.force_diner_fade` with its unit test was written and passed, then taken out of the commit) could not be measured: the machine was held by other jobs, so the three post-change runs never ran, and under the ruling ("if in doubt, report it and add nothing") the addition is NOT in the commit. Next step for whoever continues: build with `Warmup.force_diner_fade(main.world.occluder_fade, true/false)` around the warm-up's frames (it needs `OccluderFade` to expose a warm-up entry), take `?perflog=60` runs of the play-entered night (the log marks `fade_Diner@<t>`), and see whether the 113 to 129 ms frame moves to a time before the fade.

## 5. The gate reading
The author's ruling (D-292): fix the MEASUREMENT of the resumed night, add no warm-up for the window; a first-use draw is added only when the frame log shows it.

**Gate reading (proposed): a night entered by play, default window** (`PLAY_ENTERED=1`, script option, default unchanged). Three runs, build with the guard-bar addition (`play2_r1..3`; `play_r1..3` above are the build before it, the same numbers):
| | worst | avg fps | worst 3 (ms @ s) |
|---|---|---|---|
| play2 run 1 | 113 | 50.8 | 113 @52.7, 32 @54.9, 30 @28.4 |
| play2 run 2 | 116 | 50.8 | 116 @52.7, 39 @12.8, 31 @12.9 |
| play2 run 3 | 115 | 50.6 | 115 @52.7, 29 @14.7, 29 @20.4 |
| **median of 3** | **115 ms** | 50.8 | the gate (< 60 ms) FAILS on the one frame of section 4; every other frame is 26 to 39 ms |
The same night resumed from the save (the "resume hitch" reading, default script) reads 110 / 107 / 111 (`res_r1..3`, window-start frame included), 35 / 27 / 38 with `?perfglyph=1` (`glyph_r1..3`).

**Settle time for a resumed night (the option the author asked for): not derivable from these runs.** `PERF_SETTLE=<s>` (adds `perfwarm=<s>`) is implemented, default off. Data: with the window at 5 s the window-start frame is still in the top 3 (35 / 36 / 35 ms in the three A1 runs; 55 / 35 and 88 / 34 ms in the two `logw5` runs), so 5 s is not enough and I have no run at a longer settle (the Simulator slot was taken by other jobs for the last two hours, so the last batch never ran). The cause is the overlay's own first glyph draw, which does not depend on game time, so a settle is the wrong tool for it; the measured fix is `?perfglyph=1` (35 / 27 / 38 ms). Recommendation: make that prime the overlay's default (a five-line change to `ui/perf_overlay.gd`, outside this task's ruling: I did not change the default) and keep the gate on the night entered by play, where the artifact is absent anyway.

## 6. Boot warm-up cost (`?warmup=0`), three loads each (frame-log lines `phase_msec` and `stable_at`)
First playable frame = `phase_msec` (engine ticks at the phase change, after the warm-up) + 1000 x `stable_at` (when the boot fade lifts: 10 frames in a row under 50 ms).
| | run 1 | run 2 | run 3 | mean |
|---|---|---|---|---|
| warm-up on: phase_msec / stable_at | 3624 / 1.78 | 3577 / 1.75 | 3629 / 1.79 | |
| warm-up on: first playable (s) | 5.40 | 5.33 | 5.42 | 5.38 |
| `?warmup=0`: phase_msec / stable_at | 1669 / 3.02 | 1690 / 2.93 | 1689 / 3.00 | |
| `?warmup=0`: first playable (s) | 4.69 | 4.62 | 4.69 | 4.67 |
The warm-up costs 0.71 s of load to first playable frame (it delays the phase change by 1.95 s but shortens the load freeze after it from 2.6 s to 1.5 s). What it buys (frame log, `w0_r1..3` against `lognight_r1..3`): without it the first seconds hold 2487 to 2601 ms (the freeze), 178 and 154 ms at 2.8 s (2 of 3), and in the resumed night 116 / 118 / 118 ms at 12.7 to 12.8 s and 99 / 97 / 96 ms at 14.2 to 14.3 s (the first kill, `fx_poof` and `fx_hit` at 14.1 to 14.2 s); with it, the freeze is 1.5 s and the 12 s and 14 s frames are gone (13.2 s: no frame of 30 ms or more).
